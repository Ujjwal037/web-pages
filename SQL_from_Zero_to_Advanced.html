SQL from zero ➔ interview: why, how, where — with a real sample database

This version is written for someone who wants to master SQL from the ground up, all the way to advanced architectural concepts. Every major idea is explained conceptually, demonstrated with expertly crafted SQL on a unified sample database, and then connected to interview expectations and real-world production systems.

Must know Interview Production DB

0. How to read this page (Beginner map)

Big picture in one paragraph: A database is a highly optimized storage engine that keeps data in structured tables (similar to Excel sheets, but capable of handling billions of rows). SQL (Structured Query Language) is the declarative language used to communicate with this engine. You use it to ask questions ("show me employees in engineering") and manipulate state ("increase Ben's salary"). Interviews test your ability to retrieve data efficiently, combine entities logically, and understand the architectural impact of your queries under massive concurrency.

1 First: Read Sample database. Memorize the 3 tables and the 5-6 people. Every example in this guide relies on this specific data model.

2 Then: Fundamentals -> Joins -> Group By. Mastering these three concepts alone will allow you to pass ~50% of standard data interview questions.

3 Then: Window functions -> CTE -> Subqueries. These advanced analytical features are the primary differentiators between junior and mid/senior-level engineers.

4 Then: Indexes, EXPLAIN, ACID, locks. These answer the critical "what happens in production" questions when multiple users hit the database simultaneously.

5 Finally: Section 19 (replication / sharding) — how enterprise companies keep databases highly available, resilient, and blazing fast under immense load.

Expert Note: While MySQL, PostgreSQL, SQL Server, and Oracle all speak "SQL", they have dialectal differences (e.g., LIMIT in Postgres vs TOP in SQL Server, or varying support for `FULL OUTER JOIN`). The concepts taught here are universal. Where dialects significantly differ, this guide points it out.

1. SQL Fundamentals Must know 100%

SQL is declarative. You tell the engine what you want, and the query optimizer figures out the how. Here are the core verbs:

SELECT (The Projection): Determines which columns to return. Using SELECT * is an anti-pattern in production because it wastes memory and network bandwidth returning data the application doesn't need.

SELECT name, salary FROM employees; -- Best practice
SELECT * FROM employees; -- Avoid in production code

WHERE (The Filter): Keeps only rows that evaluate to TRUE. This happens before any grouping or sorting. This is where indexes are utilized.

SELECT name FROM employees WHERE salary >= 70000;
-- Returns: Ana, Ben, Cia, Ben

DISTINCT (Deduplication): Removes duplicate rows from the final result set. It requires the database to sort or hash the results behind the scenes, making it computationally expensive.

SELECT DISTINCT name FROM employees; 
-- Returns 5 rows (Ben is only listed once)

ORDER BY (Sorting): Orders the final output. Can sort ASC (ascending, default) or DESC (descending). You can sort by multiple columns.

SELECT name, salary FROM employees ORDER BY salary DESC, name ASC;

LIMIT / TOP / FETCH (Pagination): Restricts the number of returned rows. Crucial for web apps (e.g., "Show top 10 results").

-- PostgreSQL / MySQL
SELECT name FROM employees ORDER BY salary DESC LIMIT 1;
-- SQL Server
-- SELECT TOP 1 name FROM employees ORDER BY salary DESC;

IN & BETWEEN: IN matches any value in a specific list. BETWEEN is for inclusive ranges.

SELECT name FROM employees WHERE dept_id IN (10, 20);
SELECT name FROM employees WHERE hire_date BETWEEN '2020-01-01' AND '2021-12-31';

LIKE (Pattern Matching): Used for text search. % represents zero or more characters. _ represents exactly one character. Expert tip: Leading wildcards (e.g., '%en') prevent index usage and force a slow full table scan.

SELECT name FROM employees WHERE name LIKE 'B%'; -- Finds both 'Ben's

IS NULL (The Beginner Trap): In SQL, NULL represents an unknown or missing value. It is NOT zero, and it is NOT an empty string. You cannot use = NULL. Anything compared to NULL with an equals sign evaluates to UNKNOWN, which filters out the row.

SELECT name FROM employees WHERE dept_id IS NULL; -- Correct (Returns Eve)
-- SELECT name FROM employees WHERE dept_id = NULL; -- WRONG (Returns nothing)

Logical order of operations

You write SQL in one order, but the database executes it in another. This is why you cannot use a `SELECT` alias in a `WHERE` clause—the `WHERE` clause happens before the alias is even created!

  1. FROM / JOIN: The DB gathers the base tables.
  2. WHERE: Filters out rows that don't match the condition.
  3. GROUP BY: Rolls rows up into aggregate buckets.
  4. HAVING: Filters the aggregated buckets.
  5. SELECT: Evaluates expressions, math, and assigns aliases.
  6. ORDER BY: Sorts the final derived list.
  7. LIMIT: Chops off the top N rows.

2. Joins Most asked

Relational databases split data to avoid redundancy (Normalization). Joins are how we stitch that data back together. The ON clause dictates how the tables relate.

INNER JOIN (Intersection)

Only returns rows where a match exists in both tables. If an employee has no department (Eve), or a department has no employees (HR), they are dropped.

SELECT e.name, d.department_name 
FROM employees e 
INNER JOIN departments d ON e.dept_id = d.department_id;
-- Eve is missing. HR is missing.

LEFT JOIN (Keep the Left)

Returns all rows from the left table (`employees`), plus matched rows from the right table. If there is no match on the right, the right columns are populated with `NULL`.

SELECT e.name, d.department_name 
FROM employees e 
LEFT JOIN departments d ON e.dept_id = d.department_id;
-- Eve is included. Her department_name is NULL. HR is still missing.

RIGHT JOIN & FULL OUTER JOIN

RIGHT JOIN is the exact opposite of a Left Join (keeps all departments, meaning HR shows up with NULL employees). FULL OUTER JOIN keeps everything from both sides (Eve is there with a NULL dept, and HR is there with a NULL employee).

SELF JOIN (Hierarchies)

Joining a table to itself. You must use aliases (e.g., `e1` and `e2`) so the database knows which version of the table you are referring to. Crucial for manager-employee relationships.

-- Find employees and their manager's name
SELECT emp.name AS employee, mgr.name AS manager
FROM employees emp
LEFT JOIN employees mgr ON emp.manager_id = mgr.id;
-- Ana's manager will be NULL because of the LEFT JOIN.

CROSS JOIN (Cartesian Product)

Matches every row in table A with every row in table B. 6 employees x 3 departments = 18 rows. Rarely used in production unless generating combinations or calendar tables.

3. Aggregations & Grouping

Aggregations take multiple rows and smash them into a single summary value (e.g., COUNT, SUM, AVG, MAX, MIN).

GROUP BY

When you want aggregates per category (e.g., average salary per department), use GROUP BY. Every column in your SELECT clause that is NOT inside an aggregate function MUST be listed in the GROUP BY clause.

SELECT dept_id, COUNT(*) as headcount, AVG(salary) as avg_pay
FROM employees
GROUP BY dept_id;
-- Note: Eve is grouped into a bucket where dept_id is NULL.

WHERE vs HAVING (Critical Interview Concept)

WHERE filters individual rows before they are grouped. HAVING filters the aggregated buckets after they are grouped.

SELECT dept_id, AVG(salary) 
FROM employees
WHERE salary > 50000       -- 1. Discard anyone making <= 50k before doing math
GROUP BY dept_id           -- 2. Put remaining people into department buckets
HAVING AVG(salary) > 70000; -- 3. Discard buckets whose average is <= 70k

4. Subqueries

A query nested inside another query. Used when you need a dynamic value to filter against.

Scalar Subquery (Returns 1 row, 1 column)

-- Who makes more than the overall average?
SELECT name, salary FROM employees 
WHERE salary > (SELECT AVG(salary) FROM employees);

Nested Subquery (Returns a list of values)

-- Find employees in Melbourne
SELECT name FROM employees 
WHERE dept_id IN (
    SELECT department_id FROM departments WHERE location = 'Melbourne'
);

Correlated Subquery

The inner query references a column from the outer query. It acts like a loop, executing the inner query once for every row in the outer query. These can be very slow if not properly indexed.

-- Find employees who make more than THEIR specific department's average
SELECT e1.name, e1.salary, e1.dept_id
FROM employees e1
WHERE e1.salary > (
    SELECT AVG(salary) 
    FROM employees e2 
    WHERE e2.dept_id = e1.dept_id -- The correlation link
);

EXISTS

Used to check for the existence of rows. It is highly optimized because it stops scanning the moment it finds a single matching row (boolean short-circuiting).

-- Find departments that actually have employees
SELECT department_name FROM departments d
WHERE EXISTS (
    SELECT 1 FROM employees e WHERE e.dept_id = d.department_id
);

5. CTE (Common Table Expressions)

A CTE (declared with the WITH keyword) allows you to define a temporary, named result set at the top of your query. It makes complex logic vastly more readable than deeply nested subqueries.

WITH EngineeringStaff AS (
    SELECT id, name, salary FROM employees WHERE dept_id = 10
),
HighEarners AS (
    SELECT name FROM EngineeringStaff WHERE salary > 75000
)
SELECT * FROM HighEarners;

Recursive CTEs

Used to walk hierarchical data (like trees, org charts, or graphs). It consists of an anchor member (the root) and a recursive member (how to find the children) unioned together.

WITH RECURSIVE OrgChart AS (
    -- Anchor: Find the big boss (Ana)
    SELECT id, name, manager_id, 1 as level 
    FROM employees WHERE manager_id IS NULL
    
    UNION ALL
    
    -- Recursive step: Join to find people managed by the previous level
    SELECT e.id, e.name, e.manager_id, o.level + 1
    FROM employees e
    INNER JOIN OrgChart o ON e.manager_id = o.id
)
SELECT * FROM OrgChart ORDER BY level;

6. Window Functions Differentiator

Unlike GROUP BY, which collapses rows, Window Functions perform calculations across a set of rows related to the current row, while keeping all original rows intact.

Ranking (ROW_NUMBER vs RANK vs DENSE_RANK)

SELECT name, salary, dept_id,
    ROW_NUMBER() OVER(PARTITION BY dept_id ORDER BY salary DESC) as row_num,
    RANK() OVER(PARTITION BY dept_id ORDER BY salary DESC) as rank,
    DENSE_RANK() OVER(PARTITION BY dept_id ORDER BY salary DESC) as dense
FROM employees;
  • ROW_NUMBER: Always strictly sequential (1, 2, 3, 4). Ties are broken arbitrarily.
  • RANK: Ties get the same number, but leaves gaps (1, 2, 2, 4).
  • DENSE_RANK: Ties get the same number, NO gaps (1, 2, 2, 3).

LAG and LEAD

Allows you to compare the current row to the previous (LAG) or next (LEAD) row without a complex self-join. Heavily used in time-series analysis (e.g., month-over-month growth).

SELECT order_date, amount,
    LAG(amount) OVER(ORDER BY order_date) as previous_order_amount,
    amount - LAG(amount) OVER(ORDER BY order_date) as difference
FROM orders
WHERE customer_id = 'C1';

7. Set Operations

While JOINs combine tables horizontally (adding columns), Set Operations combine results vertically (stacking rows). Both queries must return the exact same number of columns with compatible data types.

UNION vs UNION ALL

SELECT name FROM employees WHERE dept_id = 10
UNION
SELECT name FROM employees WHERE salary > 60000;

UNION automatically removes duplicate rows from the final output. Because it has to sort/hash the data to find duplicates, it is slower. UNION ALL blindly glues the datasets together, keeping duplicates. Expert tip: Always use UNION ALL unless you specifically need deduplication for performance.

8. Constraints

Data integrity is paramount. Application code has bugs; constraints ensure bad data physically cannot be written to the disk.

  • PRIMARY KEY: Uniquely identifies a row. Inherently enforces NOT NULL and UNIQUE. A table can only have one PK (though it can be composite, spanning multiple columns).
  • FOREIGN KEY: Ensures referential integrity. An employee's dept_id MUST exist in the departments table (or be NULL). Prevents "orphan" records.
  • UNIQUE: Ensures all values in a column are different. (e.g., email addresses).
  • CHECK: Custom boolean logic. CHECK (salary > 0).

9. Indexes (deep) Very important

An index is a separate, specialized data structure (usually a B-Tree) that keeps pointers to table rows sorted by a specific key. Without an index, querying WHERE name = 'Dan' requires a Full Table Scan (reading every row on disk). With an index, the DB traverses the B-Tree in O(log N) time to find Dan instantly.

Clustered vs Non-Clustered Indexes

  • Clustered Index: This dictates the actual physical order of the data on the disk. A table can only have ONE clustered index (usually the Primary Key). When you search by PK, the database finds the data directly at the leaf node.
  • Non-Clustered (Secondary) Index: A separate structure. The leaf nodes contain the indexed value (e.g., name) and a pointer back to the actual row data (the clustered key). Finding data this way is slightly slower because it requires a "bookmark lookup" back to the main table.

The Cost of Indexes

Indexes drastically speed up SELECT queries, but they slow down INSERT, UPDATE, and DELETE operations. Every time you write data to the table, the database must synchronously update the B-Tree structures of every index attached to that table. Over-indexing a high-write table will crush database performance.

10. Query Optimization

When a query is slow, experts use EXPLAIN (or EXPLAIN ANALYZE in Postgres to run and time it) to read the database execution plan.

  • Sequential/Table Scan: Reading every row. Bad for massive tables, fine for tiny configuration tables.
  • Index Seek: Navigating the B-Tree to find a specific range of rows. The holy grail of performance.
  • Index Scan: Reading the entire index leaf-level. Better than a table scan because the index is smaller in memory, but worse than a Seek.
  • Hash Join vs Nested Loop: If the DB joins massive tables, it creates an in-memory Hash table (Hash Join). If joining a tiny table to a big indexed table, it loops through the tiny one and looks up the big one (Nested Loop).

11. Normalization

Normalization is the process of structuring data to minimize redundancy and prevent anomalies on updates/deletes.

  • 1NF (First Normal Form): Atomic values. No arrays or comma-separated lists in a single cell.
  • 2NF: Must be 1NF, and all non-key attributes must depend on the ENTIRE primary key (matters mostly for composite keys).
  • 3NF: Must be 2NF, and no transitive dependencies. (e.g., If Table has EmpID, DeptID, DeptLocation, the location depends on DeptID, not EmpID. Move Location to the Departments table).

Denormalization: In massive read-heavy reporting systems (Data Warehouses), joining 8 normalized tables is too slow. Engineers intentionally duplicate data (denormalize) to create flat, wide tables for faster read performance.

12. Transactions & ACID

A transaction wraps multiple SQL statements into a single, atomic unit of work.

BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT; -- Or ROLLBACK if an error occurs
  • A - Atomicity: All statements succeed, or none succeed. No half-finished transfers.
  • C - Consistency: Database constraints (like balances must be > 0) are valid before and after.
  • I - Isolation: Concurrent transactions don't interfere. User B doesn't see User A's uncommitted data (depending on isolation levels like Read Committed or Serializable).
  • D - Durability: Once COMMIT returns success, the data is permanent, surviving immediate power failures via Write-Ahead Logging (WAL).

13. Locks & Concurrency

To provide Isolation, databases use locks.

  • Shared (Read) Locks: Multiple readers can hold this. Writers are blocked.
  • Exclusive (Write) Locks: Only one transaction can hold this. Blocks all other readers and writers from that row/table.
  • Deadlocks: Transaction 1 locks Row A and needs Row B. Transaction 2 locks Row B and needs Row A. They wait forever. The DB detects this, kills one transaction (the victim), and forces the application to retry.

14. Views

A View is a stored SQL query that acts like a virtual table. It hides complexity and secures underlying data (e.g., hiding the salary column).

CREATE VIEW public_employee_directory AS
SELECT id, name, dept_id FROM employees; -- Salary excluded

SELECT * FROM public_employee_directory;

Materialized Views: Unlike a standard view which runs the query dynamically every time, a Materialized View physically computes and stores the results on disk. It makes heavy analytical queries instant, but the data becomes stale and must be manually refreshed (REFRESH MATERIALIZED VIEW).

15. Procedures & Functions

Stored Procedures and Functions store business logic directly inside the database engine. This reduces network round-trips but couples your architecture tightly to the specific database vendor (e.g., PL/pgSQL in Postgres, T-SQL in SQL Server).

  • Procedures: Designed for executing actions. They can handle transactions (BEGIN/COMMIT), execute complex ETL flows, and modify state without returning a specific value.
  • Functions: Designed to compute and return a value. Must be deterministic and usually cannot modify state or run transactions. They can be used directly in SQL SELECT statements (e.g., SELECT calculate_tax(salary) FROM employees).

16. SQL Data Types

Choosing the correct data type is critical for indexing efficiency and disk space.

  • INT / BIGINT: Standard integers. BIGINT for massive IDs.
  • DECIMAL(precision, scale) / NUMERIC: Used for financial data. E.g., DECIMAL(10,2) allows 8 digits before the decimal and 2 after. NEVER use FLOAT for money, as floating-point math causes rounding anomalies.
  • VARCHAR(n): Variable-length string. Only takes up as much disk space as the actual string length requires.
  • CHAR(n): Fixed-length string. 'YES' in CHAR(10) is padded with 7 trailing spaces. Very fast for exactly uniform data (like 2-letter state codes), bad for general text.
  • TIMESTAMP / DATETIME: Stores both date and time. TIMESTAMP often accounts for timezones automatically depending on the engine.

17. Real Interview Problem Solving

Here are the definitive solutions to the most common SQL interview challenges based on our sample data.

1. Nth highest salary (Using DENSE_RANK)

WITH RankedSalaries AS (
    SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) as rnk
    FROM employees
)
SELECT DISTINCT salary FROM RankedSalaries WHERE rnk = 2; -- 2nd highest (85000)

2. Duplicate records (Find names that appear more than once)

SELECT name, COUNT(*) 
FROM employees 
GROUP BY name 
HAVING COUNT(*) > 1; -- Returns 'Ben'

3. Employees earning more than their manager

SELECT e.name, e.salary, m.name as mgr_name, m.salary as mgr_salary
FROM employees e
INNER JOIN employees m ON e.manager_id = m.id
WHERE e.salary > m.salary; -- Returns 'Cia' (85k > Ana's 90k? No. But imagine if manager made less).

4. Top N per department (Top earner per team)

WITH DeptRanks AS (
    SELECT name, dept_id, salary,
           ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) as rnk
    FROM employees
    WHERE dept_id IS NOT NULL
)
SELECT * FROM DeptRanks WHERE rnk = 1;

5. Running total of orders for customer C1

SELECT order_date, amount,
       SUM(amount) OVER (PARTITION BY customer_id ORDER BY order_date) as running_total
FROM orders
WHERE customer_id = 'C1';

18. Database Design

Interviews often require you to design schemas on a whiteboard. Understand cardinality:

  • 1-to-1 (1:1): E.g., User & User_Profile. Enforced by putting a UNIQUE constraint on the Foreign Key.
  • 1-to-Many (1:N): E.g., Department & Employees. The Foreign Key (dept_id) always goes on the "Many" side (the Employees table).
  • Many-to-Many (M:N): E.g., Students & Courses. Relational databases cannot handle M:N directly. You must create a third "Junction" or "Mapping" table (Enrollments) with foreign keys pointing to both Students and Courses.

19. Real-time / production database concepts Advanced

Mid-to-senior interviews move beyond syntax and focus on distributed systems and system architecture.

19a. Replication

A single database server represents a Single Point of Failure (SPOF) and has finite read capacity. Replication solves this by streaming the transaction logs (WAL) from a Primary node to one or more Replica nodes.

  • High Availability: If the Primary crashes, a Replica is instantly promoted to become the new Primary.
  • Read Scaling: The application routes all heavy SELECT queries to the Replicas, leaving the Primary dedicated to handling INSERT/UPDATE/DELETE traffic.
  • Replication Lag: In async replication, the replica might be milliseconds behind. If a user updates their profile (write to Primary) and refreshes the page (read from Replica), they might see stale data. System architects must handle this tradeoff.

19b. Sharding and Partitioning

When a table hits billions of rows, indexes become too large to fit in RAM, and a single server's disk I/O becomes the bottleneck.

  • Partitioning: Logical separation on the same physical server. You can partition an `orders` table by month. Queries looking for January data only scan the January partition, ignoring the rest.
  • Sharding: Physical separation across different servers. You might route Customers A-M to Server 1, and N-Z to Server 2. This allows infinite horizontal scaling but makes joins across shards incredibly difficult or impossible at the database level.

19c. HA, pooling, and caching

  • Connection Pooling: Opening a TCP connection to Postgres takes precious milliseconds. If 500 web server threads open connections simultaneously, the database runs out of RAM. A connection pooler (like PgBouncer) acts as a middleman, maintaining a small, warm pool of 20 connections to the database and multiplexing the 500 app requests through them.
  • Caching (Redis): Databases hit disk. Caches hit RAM. If a query calculates the top 10 products and takes 2 seconds, the application should cache the result in Redis for 5 minutes. The DB is spared the load, but the app must tolerate 5 minutes of data staleness.

80/20 Interview Preparation Plan

Focus 80% of your time on these core areas to maximize interview success:

  1. Master JOINs completely. Understand why LEFT JOIN behaves differently when conditions are in the ON clause versus the WHERE clause.
  2. Understand the execution order: WHERE filters rows, GROUP BY creates buckets, HAVING filters buckets.
  3. Write Window Functions (ROW_NUMBER() OVER(PARTITION BY x ORDER BY y)) fluently on a whiteboard. It solves almost all "Top N" problems.
  4. Use CTEs instead of nested subqueries to show clean, maintainable coding standards.
  5. Be able to explain how a B-Tree Index speeds up reads but slows down writes, and when a Full Table Scan is actually faster than an Index Seek.
  6. Understand ACID properties and why transactions are mandatory for financial systems.
